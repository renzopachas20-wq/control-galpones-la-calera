# Seguridad de autenticación y administración

## Identidad y sesiones

El navegador utiliza Firebase Authentication con correo y contraseña, o Google mediante ventana emergente y redirección. Envía el ID token. Firebase Admin SDK verifica firma, proyecto, vencimiento, revocación y estado de la cuenta con verifyIdToken(token, true). La API compara el UID del token con el ID y el campo uid del perfil, comprueba active y autoriza el rol. El UID principal está protegido contra degradación, desactivación y cambios de credenciales por otros administradores.

El proveedor real del ID token debe estar permitido por authMethod en la API. password acepta password, google acepta google.com y both acepta cualquiera de los dos. Un perfil heredado sin authMethod se interpreta como password. En perfiles establecidos, un cambio de método requiere que la cuenta de Firebase tenga al menos un proveedor compatible. both permite preparar el segundo proveedor sin cambiar de UID. Para convertir una cuenta Google ya vinculada, autorizar both y luego asignar contraseña por UID. Cambiar de método establece un corte operativo local. La contraseña temporal se reserva para perfiles vinculados que admiten contraseña.

La API guarda `sessionValidAfter` en el perfil y rechaza un token con `auth_time` anterior o igual al corte. Las reglas de Firestore cierran todas las lecturas y escrituras directas del cliente. La API lee el mismo corte que protegía el acceso directo y además consulta la revocación del proveedor. La reactivación mantiene el perfil inactivo hasta confirmar Auth y establece un corte nuevo, estrictamente mayor que el anterior incluso dentro del mismo segundo. Un nuevo inicio de sesión debe producir un `auth_time` posterior al corte.

La revocación explícita, la desactivación y la reactivación coordinan los envíos con las mutaciones de credenciales. Escriben `validSince` por UID y conservan el mayor corte confirmado. El cambio de correo o contraseña también actualiza el corte operativo al confirmar. Firebase puede revocar por una acción de consola, otro cliente Admin SDK, cambios de credenciales fuera de la aplicación o recuperación autónoma sin modificar el perfil. Firestore Rules carece de una consulta de revocación a Auth. Cerrar el canal directo y comprobar revocación en cada petición cubre ese caso con los servicios existentes, sin una réplica adicional de sesiones. La verificación de Auth ocurre al autorizar la petición. Una revocación externa posterior a esa comprobación no cancela retroactivamente una petición en curso. Un cambio local de perfil y una mutación operativa se ordenan con las transacciones de Firestore. [Identidad y validación del corte](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v1/projects.accounts/update) · [Revocación de sesiones](https://firebase.google.com/docs/auth/admin/manage-sessions).

Una sesión ya abierta puede conservar datos y operaciones locales sin conexión. Tras reconectar, cada lectura o reenvío pasa por la API con un ID token de esa misma sesión. La consulta del perfil cada 10 segundos distingue una denegación de autorización de un fallo de conexión. La denegación cierra la sesión. La restauración tras una recarga requiere una verificación inicial. El cliente mantiene la revisión de perfil más alta de la generación vigente. El inicio con correo o Google delega la publicación del perfil al observador de Auth. La vista previa por evento se retiró y la redirección de Google registra únicamente códigos de una lista permitida.

## Desactivación de emergencia

`POST /api/admin/users/:uid/emergency-disable` recibe un UUID. La transacción valida al administrador, protege al principal y prohíbe la autodesactivación. Guarda un registro independiente, aplica `active=false` y aumenta `sessionValidAfter`, `securityVersion` y `profileVersion`. Conserva las reservas de correo y sesiones anteriores. El registro transaccional basta para el bloqueo aunque falle la bitácora, que se escribe por separado con un ID determinista. Los perfiles temporales se gestionan en su flujo habitual porque todavía no tienen una cuenta de Auth.

La desactivación y la reconciliación exigen `verifyIdToken(token, true)` para el solicitante, seguido de la comprobación del UID, perfil activo, rol de Administrador y corte local. Si Firebase no puede confirmar la vigencia de la sesión, la API devuelve `503 AUTHORIZATION_UNAVAILABLE` antes de reservar o mutar la cuenta objetivo. Una vez autorizado el solicitante, un fallo de Authentication sobre el objetivo conserva el bloqueo en Firestore y deja pendientes los efectos sin confirmar.

El proveedor recibe `disableUser=true` y `validSince` por UID en una sola solicitud. El adaptador omite `customAttributes` para preservar la marca de credenciales. `operation.profileApplied`, `operation.authDisabled` y `operation.refreshRevoked` describen el resultado del UUID. `user` describe la última lectura del perfil y `currentAuthentication` describe si Auth estaba deshabilitado en la consulta para esa revisión. Si falla la consulta o cambia la revisión durante ella, el estado de Auth queda pendiente de consultar. Las dos lecturas pertenecen a servicios distintos. Al repetir un UUID completado después de una reactivación, el modal conserva el resultado histórico y muestra el perfil activo. La confirmación de revocación corresponde a ese UUID.

Un `PATCH` que desactiva y edita el correo bloquea primero y procesa la edición adicional con un UUID distinto. La hija guarda el UUID raíz. Para aceptar un reintento se comprueban la relación, UID, actor, tipo, revisión base, huella y estado. Una colisión devuelve `409 OPERATION_ID_CONFLICT`. Un cambio de contraseña se solicita en su endpoint específico con otro UUID. La confirmación de una operación anterior no puede cambiar `active` si cambió `securityVersion`. Si una reactivación ya envió una habilitación a Auth, el bloqueo local se aplica y la deshabilitación en Auth espera evidencia de que esa habilitación terminó. Una reactivación posterior exige reconciliar las reservas pendientes y no habilita una cuenta que ya estaba deshabilitada fuera del flujo.

En Operaciones, buscar primero los UUID vigentes del perfil, que se leen directamente aunque la consulta acotada del historial no los incluya. Un rechazo estructurado `PERMISSION_DENIED` y los rechazos documentados de autenticación o validación, como `EMAIL_EXISTS`, `INVALID_ID_TOKEN` y un token revocado, son evidencia de que ese envío no aplicó. En una emergencia se conserva el bloqueo local y se permite reintentar Auth después de resolver la causa. Un timeout, una conexión interrumpida, una respuesta ilegible o un error interno conservan el envío como incierto. Reconciliar verificando UID, marca cuando corresponda y corte en Auth. Si la evidencia no basta, mantener la reserva y escalar con su UUID y diagnóstico. Un resultado incierto no se reenvía ni se libera por antigüedad.

## Invitaciones y altas

Las invitaciones reservan el correo normalizado en _authEmailOwners, cuyo ID es el hash SHA-256 del correo. La vinculación hace una lectura por ese ID y una lectura del perfil correspondiente. Exige un correo verificado, un proveedor permitido y coincidencia de correo y UID con la cuenta actual de Firebase. Una transacción crea el perfil del UID real, conserva el perfil temporal con linkedUid y traslada la reserva al UID real. Los perfiles establecidos se autentican por su propio UID. Los errores de invitación sin reserva válida son genéricos.

Las invitaciones heredadas preauth_ sin índice requieren que un administrador vuelva a guardar el perfil temporal en la aplicación. Este paso verifica también las variantes históricas de mayúsculas y minúsculas y reserva el correo. Se mantienen el documento temporal, el UID y el historial. Las altas y cambios administrativos todavía comprueban duplicados heredados y DNI en una transacción. Los intentos de vinculación no recorren la colección.

Las altas por contraseña reservan UID y correo antes de la creación. El perfil está inactivo hasta confirmar el UID y correo devueltos por Auth. El listado de reservas muestra el estado y la fecha de vencimiento. El creador o el administrador principal puede reanudar o reconciliar. Una reserva vencida solo puede cancelarse si su estado confirma que no hay una solicitud incierta y Auth no encuentra cuenta por UID ni por correo. Se conserva un registro inactivo de la cancelación. Si se pierde la respuesta de creación, la recuperación por UID puede confirmar el alta existente sin crear otra cuenta.

## Cambios de correo y contraseña

Cada operación tiene UUID y versión monotónica por UID. Las instancias comparten el diario _authCredentialOperations y el identificador de la operación activa en el perfil. Firestore serializa la reserva y la transición ready a dispatching. El bloqueo no caduca. Solo la instancia que confirma esa transición puede enviar una solicitud HTTP.

La API devuelve `profileVersion` en cada perfil. Los perfiles heredados sin ese campo empiezan en `0`. `PATCH /api/admin/users/:uid` exige `expectedProfileVersion`, que el modal captura al abrir el formulario. La transacción comprueba la revisión antes de reservar un correo o una operación. Un formulario obsoleto recibe `409 STALE_PROFILE_VERSION` aunque traiga un UUID nuevo. Las ediciones directas y la confirmación de credenciales incrementan la revisión. El modal reutiliza el UUID al reenviar el mismo formulario y conserva el perfil con la revisión más alta ante respuestas fuera de orden. Si el backend no puede leer el perfil vigente tras la operación, devuelve el estado de la operación con `user: null` y `profileRefreshRequired: true`. El modal vuelve a consultar la lista. Una operación reservada se puede reconciliar desde Operaciones con el UUID del diario.

Cada UUID aceptado queda ligado a una huella SHA-256 de tipo, UID objetivo, UID solicitante, revisión y campos modificables enviados en orden fijo. La presencia de campos y el orden de las listas forman parte de la solicitud. Cualquier discrepancia devuelve `409 OPERATION_ID_CONFLICT` antes de escribir. Las operaciones antiguas sin huella solo se pueden consultar o reconciliar por su UUID mediante Operaciones. Las contraseñas temporales nuevas exigen al menos 20 caracteres con mayúsculas, minúsculas, números y símbolos. El generador agrega 144 bits de aleatoriedad criptográfica. El diario guarda un verificador scrypt con una sal aleatoria, que se compara en tiempo constante y no se devuelve al cliente. Si la clave original se pierde, solo una reserva `ready` que aún no se ha enviado puede cancelarse y sustituirse por otra con un UUID nuevo.

La mutación de Identity Platform identifica la cuenta por localId y añade el UUID al atributo de Auth caleraCredentialOperation en la misma petición que modifica el correo o la contraseña. El transporte envía una sola solicitud y carece de reintentos y redirecciones automáticos. Una respuesta perdida se reconcilia leyendo el usuario por UID y comprobando la marca y, para correo, el nuevo valor. Solo entonces una transacción completa la operación, libera la reserva anterior, actualiza el corte de sesión y permite el siguiente cambio. Una respuesta tardía consulta su propio registro. Un rechazo definitivo de Auth libera la reserva. Una respuesta ambigua sin marca mantiene el UID bloqueado. No existe una liberación por tiempo que permita a una escritura antigua competir con otra nueva.

El estado de Auth y el estado de la bitácora son independientes. Una operación confirmada conserva ese estado aunque falle el movimiento. La reconciliación puede registrar ese movimiento por ID determinista sin volver a modificar Auth. La contraseña en texto plano se usa en memoria durante el envío y la entrega al administrador autorizado. El diario y la bitácora no guardan esa contraseña ni tokens devueltos por el proveedor. Si se perdió la respuesta que contenía una contraseña generada, una vez confirmado el resultado se puede iniciar una nueva operación con otra contraseña.

El adaptador envía `returnSecureToken: true` en `projects.accounts.update`, conforme a la [referencia de Identity Platform](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v1/projects.accounts/update). Auth Emulator aceptó `true` y `false` para el cambio administrativo de correo y marca, con `200` y el mismo `localId`, sin tokens en ninguna de esas dos respuestas. Ese resultado describe el emulador. El transporte solo consume `localId` y descarta los tokens que el proveedor pudiera devolver. La confirmación sigue leyendo el usuario por UID y comprobando la marca.

El flujo depende de que las mutaciones administrativas de correo y contraseña pasen por este coordinador. La interfaz del proyecto carece de llamadas directas a updateEmail, verifyBeforeUpdateEmail o cambios de proveedor por correo. Firebase permite que clientes externos válidamente autenticados soliciten sus propios cambios de cuenta y que otros actores IAM administren cuentas. Esos escritores externos no comparten el diario. Si se detecta divergencia, el flujo detiene el cambio y requiere revisión por UID. Una operación cuya marca nunca aparece necesita evidencia del proveedor antes de liberar manualmente el bloqueo.

## Recuperación por correo

El endpoint administrativo de recuperación devuelve 410 y la acción se retiró del modal. Identity Platform identifica la cuenta de recuperación mediante su dirección de correo. Una consulta previa de UID no elimina la carrera si esa dirección se reasigna fuera de la aplicación. Se mantiene la recuperación autónoma del SDK web desde la pantalla de acceso, que entrega el enlace al titular del correo vigente. Para una cuenta solo Google, la recuperación del proveedor corresponde a Google y el acceso a la aplicación sigue sujeto al método configurado. Se conserva la asignación administrativa de contraseña por UID donde el método lo permite.

La documentación de Identity Platform describe los identificadores aceptados para cada operación. [Mutación por UID](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v1/projects.accounts/update) · [Recuperación por correo](https://docs.cloud.google.com/identity-platform/docs/use-rest-api#section-send-password-reset-email).

## Operaciones y bitácora

`GET /api/data/:collection`, `GET /api/data/:collection/:id`, `POST /api/data/snapshot` y `POST /api/data/write` usan una lista explícita de colecciones. Cada petición comprueba revocación y autoriza con el perfil de Firestore en una transacción. La matriz concede acceso por rol, módulo y acción en todos los proyectos, sectores y galpones. Los avances y movimientos conservan su autor para auditoría. La auditoría de Administración de Usuarios solo es visible para Administrador. La API valida referencias operativas, detecta ubicaciones ambiguas y combina por trabajador las actualizaciones de asistencia. Las asignaciones heredadas en perfiles se toleran en solicitudes antiguas y quedan fuera de la decisión de acceso.

Las mutaciones autorizadas generan un recibo por actor e identificador, sus movimientos inmutables y el cambio de datos en la misma transacción. Los reintentos idénticos no duplican efectos. Las revisiones operativas se comparan en esa transacción. Las eliminaciones con identificador no reutilizable dejan una marca en `_operationalDeletions`. Los movimientos de autenticación conservan su diario propio. La aplicación web no envía movimientos sueltos. El consumo de materiales se deriva de los avances confirmados, incluido un avance que un Auxiliar sí tiene permiso de registrar. La aplicación conserva las partes de un avance compartido en un mismo lote de sincronización. Los movimientos operativos reflejan cambios confirmados, sin emitir entradas para acciones locales como exportaciones.

`POST /api/data/movements/import` es el flujo separado de importación histórica controlada. Requiere un Administrador activo. Recibe `entries` con `sourceId`, `timestamp`, `module`, `type` y `detail`. Solo inserta, atribuye la importación al administrador autenticado y marca el movimiento como histórico. Un identificador de origen repetido con contenido distinto devuelve conflicto. La matriz y el menú de operaciones ordinarias conservan sus permisos.

`POST /api/data/gantt/withdraw` modifica exclusivamente `ganttExcludedActivityIds` del galpón. La transacción valida `gantt.delete`, la existencia de la actividad y la revisión del sector. La cola guarda los identificadores y la revisión sin copiar la jerarquía. Un `409 STALE_DATA_VERSION` mantiene el plan confirmado visible y permite reenviar la misma intención y UUID tras consultar la revisión vigente. Las exclusiones ya existentes se conservan al editar otros campos. Los movimientos de Gantt identifican la actividad y el galpón afectados.

La baja estructural se valida por separado de las demás mutaciones. Si quedan avances, inventario, personal, asistencia localizada o actividades vinculadas a la ubicación, devuelve `409 STRUCTURAL_DEPENDENCIES`. Los identificadores de ubicaciones retiradas se conservan en `_structuralLocations` y la baja de un galpón genera su propio movimiento. Las bajas de actividades, materiales y trabajadores con historial vinculado conservan sus referencias. Personal permite desactivar operarios y las nuevas asignaciones de un parte deben corresponder a trabajadores activos de su ubicación.

`POST /api/data/workers/import` autoriza `personal.import` incluso para una sola fila. Conserva el UUID y el contenido del lote en un recibo de la misma transacción que las altas y sus movimientos. `/api/data/write` determina si cada fila crea o edita según el estado de Firestore y exige `personal.import` si la petición contiene más de un alta de Personal. La importación XLSX se reenvía como lote. Una solicitud independiente de alta individual exige `personal.create`.

`POST /api/data/catalog/templates/duplicate` comprueba `catalogo.create` y `catalogo.view`. La transacción guarda la plantilla nueva, sus actividades, los movimientos y el recibo de la petición. El origen permanece disponible para futuras copias. Los códigos se validan dentro de la plantilla y los códigos de galpón se validan dentro del sector.

El código de Personal es único en la planilla. Se eliminan espacios exteriores y se normaliza a mayúsculas. Una reserva transaccional por código en `_workerCodes` serializa altas e importaciones concurrentes. Las altas o cambios de código comprueban también los documentos heredados dentro de la transacción. Las colisiones heredadas se conservan y bloquean nuevas altas con ese código. No se necesita rellenar el índice ni modificar registros existentes para activar la validación. Una edición que conserve el código normalizado mantiene el registro heredado. La interfaz muestra texto seguro para valores antiguos de tipo inválido.

Las solicitudes independientes autorizadas por `personal.create` siguen permitidas. Con el contrato actual, una secuencia de solicitudes individuales puede representar tanto altas manuales legítimas como la automatización de esas altas. La política por solicitud permanece igual.

La interfaz conserva las fusiones y la cola offline. Las consultas operativas se renuevan cada 15 segundos. Las cachés y vistas de cola se separan por UID y rol. La autorización operativa local caduca después del intervalo configurado desde la última comprobación correcta con el servidor. La caducidad se mantiene en memoria, y una recarga siempre requiere verificar el UID y el perfil en línea. La administración queda suspendida al perder conexión o cuando falla la comprobación del perfil. La revocación remota se conoce cuando el dispositivo vuelve a comunicarse con Firebase y la API. La sesión local no puede retirar datos que el navegador ya haya descargado.

Las operaciones locales sin autor verificable quedan en cuarentena y los movimientos antiguos en cola requieren revisión para importación. El reenvío comprueba la sesión y el rol vigente y consulta el recibo si se perdió la respuesta. La ruta genérica admite tramos de hasta 100 escrituras. Los lotes de Personal permanecen en el Centro de Sincronización hasta confirmarse. Asistencia compara el valor previo por trabajador dentro de la transacción y devuelve `ATTENDANCE_CONFLICT` ante una corrección obsoleta. El intento queda visible para su autor y el valor oficial se conserva. Las asignaciones nuevas de personal y materiales deben apuntar a sectores y galpones existentes.

## Cloud Run y pruebas locales

El cliente oficial @google-cloud/firestore recibe projectId y databaseId explícitos desde firebase-applet-config.json, sin fallback a (default). Firebase Admin SDK y el cliente de Firestore usan ADC. Cloud Run debe usar una identidad de servicio dedicada, Node 24 y NODE_ENV=production. Mantener las credenciales privadas fuera de Git, de la imagen y de las variables. La API usa IAM y aplica sus autorizaciones sin depender de Firestore Security Rules. Los clientes están sujetos a las reglas, incluidas las que protegen el diario y el índice de correos. Coordinar backend, cliente y reglas cuando se autorice el despliegue.

La API admite solicitudes del mismo origen. Si un cliente se sirve desde otro origen, configurarlo de forma explícita en `CALERA_ALLOWED_ORIGINS`. El servidor rechaza los demás orígenes antes de registrar las rutas de autenticación y datos. Las solicitudes todavía requieren el ID token y los permisos de cada ruta.

Para un rol personalizado de ejecución, partir de `firebaseauth.users.get`, `firebaseauth.users.create` y `firebaseauth.users.update` en Identity Platform. En Firestore Native, las operaciones usan `datastore.databases.get` para las transacciones y `datastore.entities.get`, `datastore.entities.list`, `datastore.entities.create`, `datastore.entities.update` y `datastore.entities.delete` para los documentos. Limitar el acceso a la base nombrada y a los procesos previstos. Verificar el conjunto en un entorno aislado. [IAM de Identity Platform](https://docs.cloud.google.com/identity-platform/docs/access-control) · [IAM de Firestore Native](https://docs.cloud.google.com/firestore/native/docs/security/iam).

Antes de aplicar las reglas, revisar la correspondencia entre los métodos declarados en los perfiles y los proveedores vinculados, especialmente para el administrador principal. Un perfil heredado cuyo proveedor real contradiga su método requiere revisión administrativa. El cambio local no reasigna identidades ni modifica perfiles automáticamente.

Queda pendiente validar en un proyecto administrado aislado la revocación externa, la revocación de refresh tokens, los intentos de renovación con un token anterior y la reautenticación después de reactivar. También quedan pendientes ADC, IAM, la base nombrada, reglas, índices, latencia y costes de la consulta periódica, y volumen y contención de las transacciones operativas. Aplicar la API y las reglas como un cambio coordinado requiere un plan de compatibilidad con los clientes de la versión anterior. Las pruebas de emulador cubren el flujo local.

Ejecutar `npm test` para la suite local. Para integración, iniciar Firestore Emulator y Auth Emulator en loopback, con el proyecto `demo-calera-phase11`. Configurar `FIRESTORE_EMULATOR_HOST` y `FIREBASE_AUTH_EMULATOR_HOST` como `127.0.0.1:puerto` y ejecutar `npm run test:security:emulator`. Las pruebas usan la base sintética `calera-audit` y cargan allí las reglas del repositorio. Para repetir la cobertura de revocación, Auth y las rutas operativas hacen falta ambos emuladores. En producción se rechazan variables de emulador.

Revisar las copias históricas de la bóveda por separado. La aplicación no lee ni escribe el archivo y Vite bloquea su entrega.
